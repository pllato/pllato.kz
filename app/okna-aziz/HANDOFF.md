# ОКНА СЕРВИС · Азиз, Бишкек

Полная техническая передача рабочего демонстрационного контура для следующего код-агента.

## 1. Назначение

Этот каталог содержит самостоятельный рабочий контур системы для оконного производства Азиза из Бишкека.

Основная идея продукта: один проект проходит полный путь от первого обращения клиента до финального расчёта, а каждое выполненное действие одновременно формирует историю проекта, KPI сотрудника, начисление и себестоимость.

Контур опубликован по адресу:

- `https://pllato.kz/app/okna-aziz/`

Карточка в главном App:

- `data-app-id="okna_crm_aziz"`
- название: `ОКНА СЕРВИС · Азиз, Бишкек`
- карточка находится во вкладке «Все»;
- права на карточку, избранное, отметка выполнения и временные ссылки обслуживаются общим механизмом `app.html`;
- доступ настраивается отдельно от других карточек.

## 2. Важное разделение контуров

Есть два независимых продукта, их нельзя снова объединять:

| Контур | URL | Исходники | Ключ данных |
|---|---|---|---|
| Ocean Glass / оригинальная ОКНА CRM | `/app/okna/` | `styles.css`, `data.js`, `ui.js`, `modules.js`, `modules2.js`, `main.js` | `okna_crm_db_v1` |
| Азиз, Бишкек / полный производственный контур | `/app/okna-aziz/` | `app.css`, `app.js` | `okna_aziz_bishkek_demo_v4` |

Правила:

1. Изменения в контуре Азиза не должны менять `/app/okna/`.
2. Изменения в Ocean Glass не должны менять `/app/okna-aziz/`.
3. Не переименовывать `okna_aziz_bishkek_demo_v4` без миграции: в нём сохраняются действия пользователя.
4. Не направлять обе карточки App на один URL.
5. Не удалять оригинальные файлы Ocean Glass из `app/okna/`.

## 3. Технический стек

- статический HTML/CSS/JavaScript;
- без npm, сборщика, фреймворка и внешней базы данных;
- вся разметка экранов формируется в `app.js`;
- данные рабочего демо сохраняются в `localStorage` браузера;
- шрифты: Golos Text и Onest через Google Fonts;
- адаптивная вёрстка реализована в `app.css`;
- общий вход App подключён через `/app/gate.js`.

Структура каталога:

```text
app/okna-aziz/
├── index.html   # точка входа, gate, шрифты, favicon, подключение CSS/JS
├── app.css      # дизайн-система, desktop/mobile, таблицы, карточки, модальные окна
├── app.js       # данные, роли, модули, рендеринг, действия и сохранение
└── HANDOFF.md   # этот документ
```

## 4. Запуск локально

Из корня репозитория:

```bash
python3 -m http.server 8000
```

Открыть:

```text
http://localhost:8000/app/okna-aziz/
```

Если локальная проверка блокируется общим `gate.js`, выполнять проверку из авторизованной сессии App или временно подменять gate только в локальной среде. Не публиковать обход авторизации.

## 5. Полезные URL-параметры

`boot()` в конце `app.js` поддерживает:

- `?reset=1` — сбросить контур к исходным демо-данным;
- `?role=director` — войти сразу под указанной ролью;
- `?module=coverage` — открыть модуль по идентификатору;
- `?project=P-1050` — открыть карточку проекта;
- `?tab=finance` — открыть вкладку карточки проекта.

Примеры:

```text
/app/okna-aziz/?role=director&module=coverage
/app/okna-aziz/?role=director&project=P-1050&tab=finance
/app/okna-aziz/?reset=1
```

| `designer` | Проектировщик | чертежи, спецификация, согласование |
| `procurement` | Закупщик | потребность, поставщики, транспорт, сроки |
| `warehouse` | Кладовщик | приход, резерв, выдача, возвраты, остатки |
| `production` | Производство | задания, операции, фактический объём |
| `qc` | ОТК | качество, замечания, возврат на переделку |

## 7. Сквозной маршрут проекта

Массив `STAGES` задаёт последовательность:

1. Продажи.
2. Замер.
3. Предоплата.
4. Проектирование.
5. Закупки.
6. Склад.
7. Производство.
8. ОТК.
9. Логистика.
10. Монтаж.
11. Финальный расчёт.

Каждый этап связан с модулем и ответственным сотрудником. `completeStage(stage, projectId)`:

1. проверяет обязательный чек-лист;
2. не даёт завершить этап при незакрытых пунктах;
3. переводит проект на следующий этап;
4. добавляет запись в журнал действий;
5. сохраняет данные;
6. открывает следующий рабочий модуль;
7. показывает уведомление пользователю.

## 8. Модули системы

### Управление

- `dashboard` — пульт директора: проекты, деньги, отклонения, сотрудники;
- `projects` — единый реестр и карточка проекта;
- `sales` — лиды, квалификация, договор и задача на замер;
- `map` — карта объектов, выездов, маршрутов и полевых сотрудников.

### Сквозной заказ

- `measure` — выезд замерщика, статусы, размеры, фото, выполненный объём;
- `design` — проектирование, чертежи, спецификация и согласование;
- `procurement` — потребность, заказ поставщику, транспорт и сроки;
- `warehouse` — приход, резерв, выдача, возврат, списание, «Мой Склад»;
- `production` — производственное задание, операции и фактический объём;
- `qc` — ОТК, фото, решение, замечания и возврат;
- `logistics` — рейсы, маршрут, километраж и доставка;
- `install` — монтаж, фото, акт и приёмка;
- `cash` — предоплата, финальная оплата, себестоимость и прибыль;
- `rework` — дефекты, переделки, виновный этап, срок и стоимость.

### Результат сотрудников

- `payroll` — выполненный объём → ставка → KPI → начисление;
- `rates` — индивидуальные расценки и срок их действия;
- `audit` — неизменяемая история действий и согласований.

### Система

- `coverage` — карта покрытия всех 33 пунктов ТЗ;
- `access` — роли, уровни видимости и матрица модулей.

## 9. Карточка проекта

`projectModal(id, tab)` открывает проект и поддерживает вкладки:

- `route` — маршрут проекта по всем этапам;
- `main` — клиент, контакты, адрес, координаты, изделие, даты, объём;
- `team` — ответственные по каждому участку;
- `docs` — договор, чертежи, фото, заказы поставщикам, ОТК, акт;
- `finance` — договор, затраты, зарплата, доставка, монтаж, прибыль, платежи;
- `history` — журнал действий по проекту.

Принцип: данные не размазываются по разным сущностям. Проект является общим контейнером для процесса, команды, документов, финансов и аудита.

8. тестовый сценарий перехода.

## 11. KPI и зарплата

Цепочка согласования начисления:

1. работа выполнена;
2. руководитель подтверждает факт и объём;
3. финансы проверяют ставку и расчёт;
4. директор утверждает начисление;
5. начисление получает статус `closed`.

`approve(id)` переводит начисление между статусами:

```text
manager → finance → director → closed
```

После каждого подтверждения создаётся запись в аудите.

Формулы, которые демонстрирует интерфейс:

- окладная;
- сдельная: объём × ставка × KPI;
- смешанная: оклад + объём + KPI.

Важно: зарплата по проекту входит в себестоимость проекта и влияет на прибыль.

## 12. Финансовая модель

`calcProfit(project)` использует:

```text
Себестоимость = материалы
              + производство
              + зарплата
              + доставка
              + монтаж
              + другие расходы

Прибыль = сумма договора − себестоимость
Маржа = прибыль / сумма договора × 100%
```

В карточке проекта показываются:

- сумма договора;
- предоплата;
- всего получено;
- остаток;
- материалы;
- производство;
- зарплата;
- доставка;
- монтаж;
- прочие расходы;
- итоговая прибыль и маржа.

## 13. Модель данных

`seed()` возвращает объект версии `v: 4`:

```js
{
  v,
  users,
  projects,
  materials,
  rates,
  accruals,
  audit,
  checks,
  selectedProject
}
```

### `users`

Основные поля:

```text
id, name, role, title
```

### `projects`

Основные группы полей:

- идентификация: `id`, `client`, `phone`, `object`;
- география: `address`, `coords`, `map`, `lat`, `lon`;
- продукт и процесс: `product`, `stage`, `status`, `plan`, `actual`, `delay`;
- команда: `manager`, `surveyor`, `designer`, `procurement`, `warehouse`, `production`, `qc`, `logistics`, `installer`;
- объём и качество: `volume`, `reworks`;
- деньги: `contract`, `prepay`, `paid`, `materials`, `productionCost`, `payroll`, `delivery`, `installCost`, `other`.

### `materials`

Материал, единица измерения, фактический остаток, минимальный остаток и источник синхронизации.

### `rates`

Сотрудник, вид работы, единица, ставка, период действия и согласующий.

### `accruals`

Проект, сотрудник, работа, объём, единица, ставка, KPI и статус согласования.

### `audit`

Время, пользователь, действие и проект.

### `checks`

Массив логических значений по каждому этапу. Индексы соответствуют пунктам `CHECKLISTS[stage]`.

## 14. Сохранение данных

Рабочее состояние хранится в:

```js
const KEY = 'okna_aziz_bishkek_demo_v4';
```

Функции:

- `load()` — читает данные или создаёт seed;
- `save()` — сохраняет актуальный объект `DB`;
- `?reset=1` — пересоздаёт seed и перезаписывает сохранённое состояние.

Ограничения текущей версии:

- данные локальны для конкретного браузера и профиля;
- между устройствами они не синхронизируются;
- одновременная работа нескольких пользователей не реализована;
- нет серверных конфликтов и истории версий объекта;
- выгрузки и загрузки файлов в демо визуальные, без файлового хранилища.

Если контур переводится из демо в рабочий продукт, первым архитектурным шагом должна быть серверная модель данных и авторизация по пользователям. Не пытаться строить многопользовательскую эксплуатацию поверх `localStorage`.

## 18. Проверка перед публикацией

Минимальный чек-лист:

1. `/app/okna/` всё ещё открывает оригинальную Ocean Glass CRM.
2. `/app/okna-aziz/` открывает отдельный контур Азиза.
3. Изменение чек-листа Азиза не влияет на Ocean Glass.
4. Сброс Азиза не сбрасывает Ocean Glass.
5. В App присутствуют две разные карточки и два разных `data-app-id`.
6. В правах пользователя есть отдельный пункт Азиза.
7. Избранное и отметка выполнения одной карточки не меняют другую.
8. Временная ссылка карточки Азиза ведёт на `/app/okna-aziz/`.
9. Роль директора видит `coverage` и `access`.
10. Обычная роль не видит закрытые для неё финансовые модули.
11. Все локальные CSS/JS-файлы возвращают HTTP 200.
12. На ширине 390 px интерфейс остаётся рабочим.

## 20. Требования к дальнейшим изменениям

- Сохранять визуальный язык: тёмный хвойный, тёплый золотой, светлые рабочие поверхности.
- Не превращать страницы в набор несвязанных дашбордов: главным объектом остаётся проект.
- Не дублировать ввод данных между этапами.
- Не давать сотруднику самостоятельно подтверждать собственное начисление.
- Финансовые поля должны быть закрыты ролями.
- Любое изменение денег, ставки, KPI или объёма должно попадать в аудит.
- Удаление важных сущностей заменять аннулированием или корректировкой с причиной.
- Сохранять мобильный сценарий полевого сотрудника.
- Не добавлять зависимости без необходимости: текущий контур работает без сборки.
