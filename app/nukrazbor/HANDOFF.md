# NUK Control · BMW авторазбор (Нурлан)

Полная техническая передача двух связанных HTML-демо для следующего код-агента.

## 1. Назначение

Этот контур демонстрирует единую систему управления BMW-авторазбором NUK в Алматы.

Внутри показан полный путь денег и детали:

1. поступает автомобиль-донор или контейнер;
2. автомобиль проходит диагностику и разбор;
3. каждая деталь получает карточку, OEM, применимость, фото и адрес полки;
4. остаток публикуется во внутреннем каталоге и на клиентской витрине;
5. обращение из сайта, WhatsApp, звонка или рекламы превращается в сделку;
6. резерв защищает от двойной продажи;
7. собственник видит окупаемость донора, возраст остатков и точки для ускорения выручки.

Рабочие URL:

- внутренний пульт: `https://pllato.kz/app/nukrazbor.html`;
- клиентская витрина: `https://pllato.kz/app/nukrazbor-catalog.html`.

Карточка в App:

- `data-app-id="nuk_auto_control"`;
- название: `NUK Control · BMW авторазбор (Нурлан)`;
- доступ, избранное, отметка выполнения и временные ссылки обслуживаются общим механизмом `app.html`.

## 2. Два интерфейса одного продукта

| Интерфейс | Точка входа | Назначение |
|---|---|---|
| Внутренний NUK Control | `app/nukrazbor.html` | Работа собственника, цеха, склада, продаж и маркетинга |
| Клиентский каталог | `app/nukrazbor-catalog.html` | Поиск запчасти, проверка совместимости, карточка товара и резерв |

Оба интерфейса используют один набор демо-данных:

```text
app/nukrazbor/data.js → window.NUK_DATA
```

Правила:

1. Не разрывать связь внутренних остатков и публичной витрины.
2. Если меняется модель детали, обновлять оба интерфейса.
3. Клиентский каталог не должен показывать внутреннюю себестоимость, задачи и финансовые показатели.
4. Внутренний пульт остаётся источником правды для остатков, цены, резерва и статуса публикации.
5. Не выдавать демонстрационные интеграции за реально подключённые.

## 4. Технический стек

- статический HTML/CSS/JavaScript;
- без npm, сборщика, фреймворка и серверной базы;
- глобальный объект данных `window.NUK_DATA`;
- URL-параметры через `URLSearchParams` и History API;
- все внутренние экраны формируются функциями в `app.js`;
- клиентская витрина формируется в `catalog.js`;
- дизайн основан на Golos Text и Unbounded;
- общий контроль доступа подключён первым скриптом: `/app/gate.js`.

Внешние зависимости:

- логотип NUK загружается с внешнего URL;
- демо-фото запчастей загружаются с внешнего CDN;
- шрифты загружаются из Google Fonts.

В репозитории нет секретов, API-токенов и серверных ключей этого контура.

## 5. Локальный запуск

Из корня репозитория:

```bash
python3 -m http.server 8000
```

Открыть:

```text
http://localhost:8000/app/nukrazbor.html
http://localhost:8000/app/nukrazbor-catalog.html
```

Не открывать HTML через `file://`: абсолютные пути `/app/...` и общий gate рассчитаны на HTTP-сервер.

Если локальная проверка блокируется `gate.js`, проверять из авторизованной сессии App. Не публиковать обход авторизации.

## 6. Маршрутизация внутреннего пульта

Функция `route()` читает:

```text
?s=<раздел>&id=<сущность>&tab=<вкладка>
```

Основные ссылки:

| Параметр `s` | Экран | Функция рендера |
|---|---|---|
| `dashboard` | Пульт собственника | `renderDashboard()` |
| `dismantling` | Разбор автомобилей | `renderDismantling()` |
| `catalog` | Каталог и остатки | `renderCatalog()` |
| `receipts` | Поступления | `renderReceipts()` |
| `warehouse` | Адресный склад | `renderWarehouse()` |
| `sales` | Продажи | `renderSales()` |
| `clients` | Клиенты и диалоги | `renderClients()` |
| `tasks` | Задачи команды | `renderTasks()` |
| `analytics` | Финансы и аналитика | `renderAnalytics()` |
| `marketing` | Маркетинг и партнёры | `renderMarketing()` |
| `integrations` | Интеграции | `renderIntegrations()` |

Примеры:

```text
/app/nukrazbor.html?s=dismantling
/app/nukrazbor.html?s=catalog
/app/nukrazbor.html?s=sales
/app/nukrazbor.html?s=analytics
```

`go(s, id, tab)` обновляет URL через `history.pushState()` и вызывает `render()` без полной перезагрузки страницы.

## 7. Модель данных

`data.js` создаёт:

```js
window.NUK_DATA = {
  logo,
  warehouses,
  donors,
  parts,
  deals,
  tasks,
  referrals,
  integrations
};
```

### `warehouses`

Две точки NUK:

- Бесагаш — основной склад;
- Суюнбая — городская выдача.

Поля:

```text
id, name, address, parts, value, fill, zones
```

### `donors`

Автомобили-доноры и их экономика:

```text
id, car, year, engine, vin, origin, stage, progress,
parts, done, cost, forecast, sold, arrival, owner, color
```

### `parts`

Карточка детали:

```text
id, name, category, model, oem, cross, donor, condition,
price, cost, warehouse, place, qty, status, days, img, fit
```

Клиентская витрина использует только детали со статусами:

```text
available, reserved, discount
```

### `deals`

```text
id, client, phone, car, request, amount, stage,
source, owner, age, part
```

### `tasks`

```text
id, title, area, assignee, due, priority, status, done, total
```

### `referrals`

```text
name, code, leads, sales, revenue, reward, status
```

### `integrations`

```text
id, name, desc, status, sync
```

## 8. Донорский цикл

`donorStages` задаёт путь автомобиля:

```text
Приёмка → Диагностика → Разбор → Фото → Публикация → Завершён
```

Карточка донора показывает:

- VIN, модель, двигатель, цвет и происхождение;
- дату поступления и ответственного;
- количество потенциальных и готовых деталей;
- вложения, прогноз продаж и уже полученную выручку;
- прогресс текущего этапа.

Действие `advance-donor` в демо переводит донора на следующий этап и увеличивает прогресс. Изменение живёт только до обновления страницы.

## 9. Каталог и адресный склад

Внутренний каталог поддерживает:

- поиск по номеру NUK;
- OEM и кросс-номеру;
- названию и модели BMW;
- VIN/донору;
- складу и адресу полки;
- статусам наличия, резерва, фото и уценки.

Складской экран показывает:

- две физические точки;
- зоны хранения;
- занятость;
- стоимость остатков;
- визуальную карту ячеек;
- перемещения и инвентаризацию как демонстрационные сценарии.

Принцип: одна деталь имеет один внутренний ID, одного донора и точный адрес хранения.

## 10. Поступления

Экран `receipts` показывает:

- контейнеры и локальные поступления;
- активную приёмку;
- количество доноров и деталей;
- распознавание маркировок;
- позиции без фото;
- расхождения и задачи на проверку;
- журнал документов поступления.

Кнопки сканера, OCR, этикетки и продолжения приёмки являются интерфейсным прототипом, а не реальной интеграцией с камерой или принтером.

## 11. Продажи и клиенты

`dealStages` задаёт воронку обращения:

```text
Новая заявка → Подбор → Резерв → Оплата → Выдача/доставка → Завершено/отказ
```

Сделка связана с:

- клиентом и телефоном;
- автомобилем клиента;
- запрошенной деталью;
- карточкой остатка;
- источником обращения;
- ответственным менеджером;
- суммой и стадией.

Действие `next-deal` двигает демо-сделку дальше. Резерв и WhatsApp показывают toast/интерфейсный сценарий без серверного вызова.

## 12. Задачи команды

Задачи разделены по зонам:

- цех;
- фото-зона;
- склад;
- продажи;
- маркетинг.

Карточка хранит ответственного, срок, приоритет, статус и прогресс чек-листа. `next-task` переводит задачу по этапам:

```text
Нужно сделать → В работе → Проверка → Готово
```

## 13. Финансы и аналитика

Собственнику показаны:

- выручка;
- себестоимость;
- операционные расходы;
- EBITDA;
- вложения и прогноз по каждому донору;
- уже проданная сумма;
- процент возврата вложений;
- возраст и стоимость залежавшихся остатков.

Демонстрационные цифры находятся прямо в шаблонах `app.js` и частично рассчитываются из `window.NUK_DATA`. Перед production их нужно заменить серверными агрегатами с единым периодом и правилами расчёта.

## 14. Маркетинг и партнёры

Модуль демонстрирует:

- переходы, заявки и продажи по каналам;
- SEO-страницы каждой запчасти;
- реферальные коды СТО, клубов и блогеров;
- выручку партнёра;
- автоматическое вознаграждение;
- кампании TikTok, Instagram и BMW-сообщества.

Реферальная выплата в демо не проводится: кнопка формирует только интерфейсный результат.

## 15. Интеграции

В seed представлены:

- NUK-каталог;
- WhatsApp Business;
- IP-телефония;
- план миграции Bazon;
- Google / Search Console;
- Instagram / Meta;

Не менять эту формулировку без фактически выполненной миграции и подтверждения Нурлана.

## 16. Клиентский каталог

`nukrazbor-catalog.html` и `catalog.js` реализуют:

- hero-поиск по названию, OEM, модели и VIN;
- фильтр по BMW-серии;
- список доступных деталей;
- карточку с фото, состоянием, OEM, применимостью, донором и полкой;
- резерв на 3 дня;
- переход в WhatsApp;
- две точки самовывоза;
- отдельное обучение «Как купить».

`cart`, `activeModel` и `query` находятся в памяти страницы и сбрасываются после обновления.

## 17. Обучение внутри демо

Во внутреннем пульте есть пошаговый тур `tourSteps`.

В витрине есть отдельный `catalogTourSteps`.

Флаги завершения сохраняются локально:

```text
nuk-control-tour-v2
nuk-catalog-tour-v2
```

Для повторной проверки тура удалить соответствующий ключ из `localStorage`.

## 18. Что реально меняется, а что является прототипом

В рамках открытой страницы реально работают:

- навигация и URL;
- поиск и фильтры каталога;
- открытие карточек деталей, доноров, сделок, задач и интеграций;
- перевод демо-донора, сделки и задачи на следующий этап;
- счётчик корзины/резерва;
- модальные окна, drawer, toast и обучение.

После перезагрузки бизнес-изменения сбрасываются к `data.js`.

Прототипами без backend остаются:

- синхронизация между устройствами;
- реальный складской учёт;
- резерв, оплата и списание;
- WhatsApp и телефония;
- OCR, камера, сканер VIN и печать этикетки;
- импорт Bazon;
- SEO/Meta/TikTok/Kolesa API;
- экспорт документов и финансовых отчётов;
- роли и серверные права внутри NUK.

## 19. Сохранение и следующий архитектурный шаг

Текущие бизнес-данные не сохраняются. `localStorage` используется только для признака завершённого обучения.

Для перехода в рабочий продукт нужно:

1. создать tenant NUK и серверную модель данных;
2. подключить App-пользователей и роли;
3. вынести доноров, детали, склады, сделки, задачи и партнёров в базу;
4. сделать резерв транзакционным, чтобы исключить двойную продажу;
5. связать внутренний остаток и публичный каталог через API;
6. добавить файловое хранилище фото и документов;
7. подключать внешние каналы только через серверный слой и секреты;
8. провести миграцию Bazon через контрольную сверку и журнал ошибок.

## 21. Контрольный чек-лист

1. `/app/nukrazbor.html` возвращает HTTP 200.
2. `/app/nukrazbor-catalog.html` возвращает HTTP 200.
3. `data.js`, `app.js`, `styles.css`, `catalog.js`, `catalog.css` возвращают HTTP 200.
4. Внутренний пульт открывает все 11 разделов.
5. URL меняется без полной перезагрузки.
6. Открываются карточки донора, детали, сделки, задачи и интеграции.
7. Внутренний поиск находит деталь по ID/OEM/модели.
8. Клиентский каталог не показывает `cost`.
9. Поиск витрины работает по названию, OEM, модели и VIN.
10. Резерв обновляет интерфейс и не выдаётся за реальную оплату.
11. Bazon помечен как план, а не как выполненная миграция.
12. Оба пошаговых обучения можно пройти и закрыть.
13. На 390 px оба интерфейса остаются рабочими.
14. `gate.js` остаётся первым скриптом в `<head>`.
15. Карточка App продолжает использовать `nuk_auto_control`.

## 22. Требования к дальнейшим изменениям

- Сохранять визуальный язык NUK: тёмно-синий, BMW-синий, красный акцент, техническая типографика.
- Не превращать продукт в общий универсальный CRM-шаблон.
- Главные сущности: донор, деталь, адрес хранения, резерв и сделка.
- Одна деталь не может одновременно быть свободной и оплаченной.
- Себестоимость и финансовая аналитика не попадают в публичную витрину.
- Каждая продажа должна сохранять источник и ответственного.
- Каждая деталь должна быть связана с донором или документом поступления.
- Любое перемещение должно иметь склад-источник, склад-получатель, сотрудника и время.
- Не добавлять секреты в браузерный код.
- Не заявлять интеграцию подключённой, пока нет реального API и контрольной проверки.
